# ThreadPilot tool specification — one table

Version 2.2 · 26 Oct 2026 (sheet-1 fixes: tools 29–30, failure modes of 1, 7–10) · supersedes the two-table layout of `TOOL_SPECIFICATION_SPRINT1.md` (kept for history). Format follows the Track 1 brief: name, input, output, the question it exists to answer, what it deliberately does not do, and how it fails. Every tool is deterministic Python over the current MySQL snapshot (CSV seeds in tests); the model picks tools and words answers, it never computes. Business date = the shared business clock (frozen at 2026-04-01 on the live site until the demo clock is started).

| # | Tool | Kind | Input | Output | Exists to answer | Deliberately does not | Failure mode |
|---|---|---|---|---|---|---|---|
| 1 | `search_orders` | Retrieval | order IDs, or customer / product / quantity / due-date filters | matching active orders with evidence rows | "How is the TrendCart order doing?" — find the order meant | pick the first match; invent an ID; search completed orders unless an ID is given | 0 matches → "no matching order"; >1 → candidate list with product, pieces, stage, days to/past due and idle days (the hint figures are in the tool result), then the next reply is narrowed on its words; "the order that was late yesterday" → the overdue candidates, never the order selected in the UI |
| 2 | `refresh_order` | Retrieval | one order ID | the current record (all fields) + evidence | "Has it moved?" — fresh fields every turn | trust earlier chat text as current data | unknown ID → "There is no order ORD-999" (an answer, not an error) |
| 3 | `summarize_orders` | Retrieval | optional stage / customer / product filter | counts by stage and status, pieces and orders per customer, active pieces, overdue (count + IDs), due today, idle-days top 5, completed on-time rate, business date | "How many orders are in progress / overdue / on time?" | revenue, prices, averages the manager did not ask a tool for; arbitrary SQL | zero-match filter → names the filter and lists the customers / products on file |
| 4 | `get_production_output` | Retrieval | stage (optional), date (ISO, yesterday, weekday name) | recorded pieces per stage that day, source row | "What was knitting output on 28 March?" | compare or judge (that is `check_normality`) | Sunday / outside the log → "no record", no number |
| 5 | `rank_active_orders` | Retrieval | criterion `idle_days` or `due_date`, optional customer, list length | active orders in that order, rule stated, idle days and days-to-due per order | "Which order has gone the longest without activity?" | score, weight or predict; treat an idle gap as a stoppage | unknown criterion → idle days, and says so |
| 6 | `list_workshops` | Retrieval | product or category, optional batch quantity | eligible outside workshops (status ACTIVE, category in `makes`, batch within cap) with queue, pickup, defect-batch probability, cost; excluded ones with the reason | "Who could take a 250-piece batch of tops?" | choose a workshop, reserve capacity, estimate the whole lead time | category not inferable → all active, rule shown |
| 7 | `compare_orders` | Retrieval | two IDs + fields (due date, last activity, stage, status, pieces, product, customer) | side-by-side refreshed records | "Compare ORD-108 and ORD-103" | weight the dimensions; pick a winner without a stated criterion | ≠2 distinct IDs → asks; no field → asks which aspect (including "overall delivery risk"); criteria named in the question are used, not asked back |
| 8 | `rank_comparison` | Judgement | the compared records + criterion (due date, last activity, or `risk` = the shared-queue projection via `assess_order_risk`) | explicit order of the active ones, rule stated; by risk: level, reason, stage, idle days per order, completed orders marked "no delivery risk", "blockers: not recorded" | "Which has the higher delivery risk, considering due date, stage, last update and blockers?" | rank completed orders as chase targets; invent blockers | criterion missing → asks "overall delivery risk, due-date pressure or update recency?" |
| 9 | `check_normality` | Judgement | stage, date, optional observed output | observed value vs the previous eight same-weekday records: min, max, mean, status below/within/above, the eight rows | "Was yesterday's assembly output normal?" | treat one low day as a fault; use a calendar average that includes Sundays; invent a cause | < 3 same-weekday samples → "insufficient baseline"; a Sunday → "closed day" (not compared); an impossible date (2026-02-31) → "not a valid date"; a future date → "no record can exist yet" + the latest record; a date after the log → the latest record, said so; a user-supplied figure that differs from the log → "The record shows X, not Y" first; no stage → all four stages compared (`stage_comparison`) |
| 10 | `explain_deviation` | Tracing | stage, date | same-day output of all stages, the normality comparison, what is missing, the next check | "Why was assembly low on 25 March?" | assert a cause: the log has no downtime, staffing or blocker fields | no record that day → says so; "is it because workshop X was suspended?" → the workshop row is quoted and the missing link stated (`list_workshops`), never confirmed |
| 11 | `assess_order_risk` | Judgement | one active order | shared-queue risk level (overdue / high / medium / low), best and expected finish dates, reason, idle days, days to due, assumptions | "Is it at risk? Why?" | call a risk a probability; call an idle gap a stoppage; forecast completed orders | insufficient capacity history → level `unknown` with the reason |
| 12 | `predict_order_delay` | Judgement | one active order | AFT delay probability + level (HIGH ≥ 0.60 / MEDIUM ≥ 0.35), expected completion, 80 % range, model weights and validation | "How likely is ORD-005 to be late? When will it really finish?" | use the current stage or the customer; forecast completed orders; replace the queue view | complete order → "applies to orders in progress" |
| 13 | `prioritize_orders` | Judgement | window days (0 = today), optional customer | active orders due in the window incl. overdue, ordered by due date → older activity → ID, each with its queue risk | "What needs attention today / this week?" | an opaque score; scanning far-future orders | window missing → asks "today only, or the next seven days?" |
| 14 | `assess_expedite` | Judgement | one active order | queue impact of moving it to the front: days saved, lateness added to others, newly-late orders, recommendation | "If we expedite ORD-017, who does it hurt?" | apply the change (manager review does that); weigh money or customer importance | any order beyond the 200-working-day horizon → "cannot quantify" |
| 15 | `estimate_capacity` | Judgement | quantity, product, due date, delivery point, optional buffer / lost packing days | verdict likely / tight / unlikely from the queue simulation with the new order inserted (best and expected case), AFT on-time chance for the size, worst-case serial sum, per-stage rates and backlogs, workshop options, assumptions | "Can we take 800 hoodies by the 25th?" | promise a date; reserve capacity; choose a workshop | delivery point missing → asks; date not in the future → asks; no capacity baseline → worst case only, labelled |
| 16 | `explain_no_data` | Refusal | the request | the stated non-goal (no prices / revenue, no workers, no causes, no delete / cancel, no customer contact) and what the system can do instead | "What revenue did TrendCart bring in?", "Delete ORD-120" | answer "which order?" to a question no order can answer | keyword guard runs only on unknown / low-confidence intents; a planner-classified `general.unanswerable` carries the reason |
| 17 | `draft_chase` | Action | order, recipient (planner / department / address), optional tone, deadline, revision | an unsent editable draft with the order's facts | "Chase it up" | send; invent a recipient or a promise | recipient missing → asks; vague deadline → asks for the exact time |
| 18 | `send_chase` | Action | a confirmed preview ID + "send now" | gateway receipt: sent / scheduled / accepted / not_sent / unknown, logged | "Send it" | send without an unexpired, matching preview; resend an unknown delivery with a new key | no gateway → `not_sent`; timeout → `unknown`, never "sent" |
| 19 | `save_internal_note` | Action | confirmed order + exact text | internal audit record on the order | "Add a note that we escalated this" | edit the order; send anything externally | stale preview or changed record → re-preview |
| 20 | `upsert_reminder` | Action | confirmed order, condition (no reply / no activity), exact time | a stored conditional watch, evaluated by the minute timer, in-app notification when unmet | "Remind me tomorrow at 2 pm if it hasn't moved" | notify outside the system; accept a vague time | past time → asks; same session / order / condition → updates in place |
| 21 | `review_reason_draft` | Action (service) | expedite analysis + drafting instruction | persisted English reason candidate, versioned | the manager's written reason for a dispatch change | change the schedule; overwrite manual edits | version conflict → reload |
| 22 | Scheduling review | Action (service) | review ID, save / apply / reject, reviewer, reason | dispatch-priority update inside ThreadPilot, logged | "Approve the expedite" | touch an external factory system; accept an AI reason as approval | preview older than 15 min or snapshot changed → rejected |
| 23 | `generate_morning_briefing` | Discovery (service) | current fact packet, business date | archived report: yesterday's production, priorities, decisions, with evidence | 07:00 "what happened, what is at risk, what needs a decision" | simulate a report when the model fails | explicit failure, no fake report |
| 24 | Alert policy | Discovery (service) | current snapshot + alert ledger | tiered decisions (P1 email now / P2 digest / P3 briefing / suppressed) with rules and reasons | "tell me only when it matters" | email more than 3 times a day; re-email an unresolved item; email on clear | dry run unless `ALERT_EMAILS_ENABLED`; Outlook missing → `not_configured` |
| 25 | `find_anomalies` | Discovery | optional stage or customer, list length | ranked findings (tier P1/P2/P3, score, title, rule, action) from the same detectors as the alert policy: sustained stage drops, stalled customers, near-due misses, overdue, high risk, single low days, idle orders; counts by kind | "Did anything go wrong yesterday?", "Anything unusual with TrendCart?" | state causes; list everything (top five by default) | no findings → says so explicitly |
| 26 | `upsert_reminder` (stage watch) | Action | stage, condition `stage_below_range`, date/time (a date alone means 07:00) | a watch keyed `STAGE:<name>`, evaluated by the minute timer with `check_normality` on the day before the deadline; in-app notification only when still below or when no record exists yet | "Remind me tomorrow if packing is still behind" | notify outside the system; treat one low day as proof | past time → asks; no record on the check day → notification says it could not be evaluated |
| 27 | Dispatch notice (service) | Action (service) | an applied expedite review | a suggested notice to the order's current department (text + the chat command that drafts it); never sent by itself | "Tell the floor about the change" | send; update an external factory system | only offered on `apply`; drafting, preview and send happen in the chat gate |
| 29 | `production_window` | Retrieval + judgement | a period in the manager's words ("since 25 March", "the last three working days", "late March", "25 to 31 March"), optional stage | one row per calendar day (Sundays "closed"), each stage's pieces against its same-weekday band, per stage: working days, days below band, first/last below, total pieces, shortfall vs the same-weekday means and vs the prior-working-day mean, both baselines named | "Has assembly been consistently below its usual level over the last three working days?", "How many pieces has assembly lost since 25 March?", "Show me the records behind the drop in late March" | sum stages together; pick one baseline silently; extend past the latest record | period after the log → capped at the latest record and labelled; `What baseline did you use?` → both rules in words with the figures |
| 30 | `stage_comparison` | Judgement | one date (defaults to the latest record when the date has no record yet) | all four stages against their own previous-eight-same-weekday band, ranked by % off the mean, the run of consecutive days below, `most_off` | "Which stage is most off its usual pace today?", "Why was output lower yesterday?" (no stage named), "What was the factory's total output on 31 March?" | add stage outputs together (the same piece passes every stage; packing is the closest thing to finished output); name a cause | no record for the date → uses the latest record and says so; a planner-invented 0-piece observation for a missing day is dropped |
| 28 | `sql_db_query` (SQL assistant) | Retrieval (separate agent) | SELECT-only SQL | rows, columns, executed SQL, truncation flag | ad-hoc questions the typed tools do not cover | write; join by guess; present a query error as a fact | AST / table / row / time limits; read-only account |

Boundaries between neighbours: `get_production_output` states a number, `check_normality` judges it, `explain_deviation` traces it, `production_window` does the same over a period and `stage_comparison` across stages; `assess_order_risk` is the queue's view of an existing order, `predict_order_delay` the size-based prior, `estimate_capacity` the view of a hypothetical one; `draft_chase` never sends and `send_chase` never drafts. The evaluation set (`evaluation/`) has at least one question on each boundary.

Access: with `MANAGER_ACCESS_TOKEN` configured, the ordinary workspace key reads and drafts but cannot confirm (`send now`, `save it`, `confirm`), apply a dispatch review, change email settings or mute alerts; the manager key can. Without it, the workspace key carries the manager role as before. `GET /api/v1/whoami` reports the role.
