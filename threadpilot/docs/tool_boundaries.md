# Where one tool ends and the next begins

The track brief says a team that ships well-specified tools "and a page of honest reasoning about the boundaries between them" will
outscore a team with a bigger model and no design. This is that page. The tool-by-tool table is `docs/tool_spec.md` (37 entries:
B1 to B18 on the live backend, D1 to D19 in the dashboard chat); this page is about the edges: when two tools could both answer, which
one does, and why the line is drawn there.

The table in the middle is not written by hand. `scripts/record_boundaries.py` asks each question of the real dashboard chat and fails
if the chat uses a different tool than the one named, so the table is what the chat did, and `tests/test_tool_boundaries_doc.py`
re-runs it. The reasoning around it is ours, and where it is a design choice and not a measurement, it says so.

## Four rules that draw every line

1. **A fact, a judgement and an estimate are three different tools, and the answer says which one it is.** A fact is read from the rows
   (`get_order`, `list_orders`). A judgement applies a rule that is written down and can be inspected (`get_stage_output`: normal is the
   mean of the previous 8 same weekdays, plus or minus the larger of 1.5 standard deviations or 5%; `list_by_risk`). An estimate carries
   its assumptions and never a plain yes (`check_feasibility`, `get_forecast`). "Late" is a fact and "at risk" is a projection, so they
   are never the same list.
2. **Reading and acting never share a tool.** A draft is a read. Sending, saving a note and creating a watch are separate tools that
   only run after the manager confirms a card that states the worst case, and each is logged. No tool both reads and writes.
3. **The model chooses the tool and words the answer; it does not compute a number, and it does not write a refusal.** Totals, bands and
   dates come from tools. The text of a refusal (`explain_no_data`) is chosen by code from the manager's own words, so a model that is
   talked into it cannot invent a price. The brief calls arithmetic by the model the single biggest source of wrong answers.
4. **When the data holds part of an answer, give that part and name what is missing; when it holds none, say so.** "Why did washing drop?"
   gets the size of the drop and "the log records output, not causes". "What is our revenue?" gets a plain no.

## Retrieval: narrow typed tools, and the failure we accepted

The brief asks whether the agent gets one `run_sql` tool or a handful of narrow ones, and to justify the choice against the failure mode
chosen. Our choice is narrow typed tools for everything the manager asks all day. The failure mode we accepted is *blindness*: a question
nobody anticipated gets "I can't answer that from this data" and the list of what it can do, never a guessed join. What we get in
exchange is that no query can silently return a wrong number, and each definition ("normal", "late", "at risk") lives in one place a
reader can inspect and a test can hold to.

The live backend also has a read-only SQL agent (`B14`, `POST /api/ai/ask`) for questions the typed tools do not cover. It accepts only
one `SELECT` on approved tables, caps the rows, runs under a database account that cannot write, and returns the query it ran. **It is a
separate endpoint that the AI page does not call.** So today the live chat has no fallback for an unanticipated question; it asks, or
refuses. Wiring the two together is a decision for Sprint 2, not something we have done.

## Where our own tools disagree

Boundaries are also the places where the design is not finished. These are real and known:

- **"Risk" now has one meaning in both chats.** It used to have three: the live path's 7-day *flag*, the dashboard chat's projected *level*
  and the Dashboard screen's priority score. The live tool `assess_order_risk` now reports the projected level from the same engine as the
  briefing (`backend/app/discovery.py`), and a test holds the two to the same level for every order on four mornings. The 7-day rule survives
  only as "review triggers", labelled as facts about what to look at. The team's Dashboard screen still ranks its task list with its own
  priority score and imported delay model; it is one screen, and its own "How is this calculated?" panel says so.
- **"Can we take it?" has two methods.** `B9` adds each stage's days in series on top of the whole backlog (very cautious). `D10` returns
  a range from the queue and the recent arrival rate, and was checked against the team's own simulator (after widening by 3 working days, 94% of ranges contained the real
  finish). The same question can get different dates from the two paths. Both state their assumptions and neither promises a date. This is
  the main disagreement left.
- **"What should I look at first?" has two orderings.** Findings ranked by score (`list_findings`, both paths) answer "what is unusual";
  the live path's `B4` orders *orders* by due date, then oldest activity, and answers "what is due". Neither is wrong; they answer different
  questions, and the classifier is told which is which.
- **One discovery engine, two moments.** The live chat's `list_findings` recomputes the eight kinds of finding from the database when asked.
  `get_briefing` reads the briefing saved at 07:00, which now carries the same findings from the same engine. They can differ only if the
  data changed since 07:00, which is the point of asking again. The 07:00 summary lines (yesterday, top issue, decide) still come from
  `dashboard_service.compose_briefing`.

## What exists on which path

| Kind | Live backend (OpenAI model + database) | Dashboard chat (rules, no model) |
| --- | --- | --- |
| Retrieval | `search_orders`, `refresh_order`, `prioritize_orders`, `compare_orders`, `rank_comparison`; `ask_database` (endpoint only) | `get_briefing_summary`, `list_orders`, `get_order`, `get_customer`, `list_customers`, `get_pipeline`, `get_on_time`, `get_forecast` |
| Judgement | `assess_order_risk`, `check_normality`, `explain_deviation`, `estimate_capacity` | `get_stage_output`, `check_feasibility`, `list_by_risk`, `assess_expedite`, `get_target_status` |
| Tracing | `evidence` (the record behind a number) | `trace_order`, plus "Show detail" on every reply |
| Discovery | `list_findings` (the same eight kinds of finding, recomputed from the database); `get_briefing` (the saved 07:00 briefing, which carries them too) | `list_findings` (eight kinds of finding, ranked) |
| Action | `draft_chase`, `send_chase`, `save_internal_note`, `upsert_reminder` | `draft_chase`, `add_note`, `create_watch` |
| Refusal | `explain_no_data` (new) | `explain_no_data` |

Discovery and the risk level are now the same on both paths. The live path still has nothing for customers, the pipeline, on-time delivery, the order forecast, expediting or stage targets. The dashboard
chat has all of them. A manager who asks the live chat "how is TrendCart doing?" gets a lookup that asks which order. That gap is real
and is the reason the dashboard chat, not the live chat, carries the recorded scenarios and the 36-question evaluation.

## What probing the boundaries found

We asked 34 questions, written after reading the routing code, and compared the tool that answered with the tool that should have.
This is a regression set, not an accuracy measure: the questions were chosen by the author, and the defects below were fixed afterwards,
so they are not part of the 24 of 36 first-pass figure.

| Found | What was wrong | Fixed by |
| --- | --- | --- |
| "Is 800 pieces from assembly normal?" | The brief's own example. The chat ignored the 800 and reported yesterday's recorded output | `get_stage_output` takes the manager's number, judges it against the same band and says it is unchecked; `tests/test_chat.py` |
| "Which customer is stalled?" | Answered with the list of idle orders, not the stalled-customer finding | Routed to `list_findings`; `list_customers` added so the customer list is a tool too |
| "Show me all orders" | "I can't answer that" for something the data can answer | Routed to `list_orders` |
| The live chat had no tool for "Did anything go wrong yesterday?" | The brief's first example question had no tool on the live path | `get_briefing` added (`briefing.today`) |
| The live chat had no way to refuse "What's our revenue?" | No intent existed for it, so the classifier could only pick an order or operation intent, or `unknown`, which asks "Which order or operation would you like to check?" (read from the code, not observed with a live model) | `explain_no_data` added (`data.unavailable`) |
| Three tool names in the spec were not the names in the code | `deviation`, `save_note` and `create_reminder` are `explain_deviation`, `save_internal_note` and `upsert_reminder` | Spec corrected; `backend/tests/test_tool_boundaries.py` checks the spec against what the engine really calls, in both directions |

## What is not measured

- **How often the live model picks the two new intents is not measured.** The server-side code is tested with a stand-in classifier that
  returns the intent a test asks for. The classifier prompt now describes `briefing.today` and `data.unavailable` and says where they stop
  (a ranked list of orders stays `order.prioritize`), but a real model may still send "what needs attention today?" the old way. Run the
  live batch once and report it as it comes out (`python3 -m evaluation.run_backend --first-pass`).
- **The dashboard chat is a set of ordered pattern rules.** A question phrased unlike the patterns falls to "I can't answer that" and the list of
  things it can do. That is the accepted failure mode above, and it is why teammates writing questions without reading the code matters.
- **The boundary table has one question per line.** It shows that each line holds for the question shown, not for every phrasing.
