# ThreadPilot 用于展示的测试方法

本手册用于现场讲解和操作。先完成 [项目启动操作手册](项目启动操作手册.md)，推荐固定业务日期为 **2026-04-01 09:00 +08:00**，使用演示数据库。

三类对话分别是：**订单决策、生产运营、执行跟进**，共 11 个子场景。以下英文可直接复制到英文界面中，中文用于讲解；模型可能追加澄清，应按实际问题回答，不必追求回复措辞完全一致。

## 1. 建议展示顺序

| 顺序 | 内容 | 建议时间 |
|---|---|---|
| 1 | 封面、Dashboard、工作台和导航 | 3 分钟 |
| 2 | 三类对话、11 个子场景 | 15–25 分钟 |
| 3 | DataGrip 修改数据，聊天与页面核对 | 5–8 分钟 |
| 4 | 本地日志、设置、导出及补充接口 | 5–10 分钟 |
| 5 | 恢复数据、记录结果 | 2 分钟 |

完整展示可以分两段：先演示三类业务对话，再演示更新与管理功能。每个编号子场景开始时点击 **New conversation**；同一子场景内不要清空会话。

所有固定数值均以未改动的种子记录为参考。实际验收以 DataGrip、回答和证据的一致性为准。

## 2. 先展示界面

| 操作 | 展示重点 |
|---|---|
| 从封面进入 Dashboard | 品牌封面、业务日期、在制／逾期／当日到期／闲置／优先级指标 |
| 切换 Production pulse 工序 | 各阶段产出趋势、历史均值与实际记录日期 |
| 点击指标或订单 | 可以进入明细、筛选和证据，而非只有静态图表 |
| 进入 AI workspace | 左侧摘要和对话记录、中间对话、右侧数据库证据 |
| 展开右侧证据 | 按回答查看稳定记录链接，打开后核对实际字段 |
| 点击左侧某个历史问题 | 定位到当前会话的对应消息 |
| 点击 Export conversation | 下载当前客户端会话 JSON，不是全部服务端历史 |
| 查看侧边栏 | Dashboard、AI workspace、Activity Log、Settings 四个入口 |

讲解时区分：Dashboard 的 Priority 分数是前端规则；AI 每日列表按到期日等明确字段排序，两者并非同一排名算法。

## 3. 场景一：订单决策（1.1–1.6）

### 1.1 模糊找订单，再逐步补充

依次输入：

1. `Show me the TrendCart order.`
2. `The scarf order.`
3. `It is the 500-piece order due on April 20, 2026.`
4. `Is it at risk?`

**看什么：** 多个候选时先追问；补充产品后能确定 ORD-005；后续的 it 延续同一订单。种子数据中活动 Scarf 已能唯一定位，不必强求系统再次询问数量。

**怎么讲：** “不用一开始填齐表单，可以通过多轮对话补充条件。”

### 1.2 查当前进度和最新记录

1. `Open order ORD-005.`
2. `What is its current stage and last activity date?`
3. `Has it moved today?`
4. `Does no update mean that no work happened?`

**看什么：** 初始记录是 KNITTING、2026-03-24；系统区分“没有记录”和“没有生产”。本场景后面会用 DataGrip 修改后重查。

### 1.3 解释风险并查看依据

1. `Is order ORD-005 at risk?`
2. `Why is it flagged?`
3. `Is it already late, or only at risk?`
4. `Show me the evidence and any available order history.`

**看什么：** 在固定演示日期下，最后活动距今 8 天，到期日仍是 4 月 20 日；风险不应直接被说成已逾期。系统没有订单事件历史时应说明缺失，不能编造停工原因。

### 1.4 比较两张订单

1. `Compare ORD-005 and ORD-021.`
2. `Compare their due dates and last activity dates.`
3. `Which one should I review first?`
4. 如果追问排序标准：`Use the earlier due date among active orders.`

**看什么：** 先确定比较维度，再给出依据。ORD-021 在种子数据中已完成，不能把它当成仍需催办的活动订单。

可补充 `Has it moved?` 展示歧义处理：同时比较两张订单后，系统应要求明确对象，再回答 `I mean ORD-005.`。

### 1.5 新订单能否按时完成

1. `Can we accept a new order for 800 TOPS pieces due on April 25, 2026?`
2. 如果询问交付点：`Delivered to the customer. Allow two working days for transport.`
3. `What assumptions are you using?`
4. `What if we lose one packing day?`
5. `What should I tell the customer?`

**看什么：** 交付点和运输缓冲被明确；有内部产能、积压、外协约束和情景变化；结果是估算，不自动承诺，也不自动分配工厂。

如果模型需要具体产品，可补充 `Crewneck sweater, category TOPS.`。不要把前端 Feasibility 页的本地模型结果要求为与 AI 模型完全相同，两者计算方式不同。

### 1.6 日报与优先处理列表

1. 点击 **Generate daily report ↗**。
2. 追问范围时输入 `Include the next seven days.`。
3. 从回复中选一个实际列出的订单，输入 `Why is ORD-xxx ranked here?`，将 ORD-xxx 替换成该订单号。
4. `Open order ORD-005.`，继续查看明细。

**看什么：** 先问范围，再列出包含逾期活动订单的清单；说明到期日、最后活动日期等排序依据；展开每一轮的证据。

日报按钮当前走订单优先级工作流，生产分析通过接下来的场景继续完成；它不是定时推送或独立的综合报告生成服务。

## 4. 场景二：生产运营（2.1–2.2）

### 2.1 产量是否正常

1. `Was assembly output normal on March 31, 2026?`
2. 如果追问比较方法：`Compare with the previous eight same weekdays.`
3. `What records support that conclusion?`
4. `Does one low day prove a sustained production problem?`

**看什么：** 种子数据中 ASSEMBLY 当日产量 455，之前 8 个同星期样本均值 745.25、范围 687–807；结论应说明低于历史范围，以及样本和判断局限。

这些数字在真实联调中核对过。如果数据库已修改，应以当前记录重新计算。也可输入 `How was assembly output yesterday?` 展示相对日期，但其含义取决于业务时钟。

### 2.2 为什么下降，下一步查什么

1. `Why was assembly output lower on March 31, 2026?`
2. `Compare knitting and assembly on that date.`
3. `Show the raw records.`
4. `What should we check next before deciding the cause?`

**看什么：** 展示当天工序数据和历史对照；把“同时出现”与“因果关系”区分开；没有人员、故障或停机记录时不凭空解释。

可补充：`Check assembly output on September 29, 2026 using the same-weekday baseline.` 在尚无该日记录时，应追问或说明数据不足，而不是沿用 3 月的数据冒充当日值。

## 5. 场景三：执行跟进（3.1–3.3）

这一类会产生真实的服务端操作。展示前使用演示环境；保存备注、创建提醒后会留下 SQLite 记录。它们不会自动出现在浏览器的 Activity Log。

### 3.1 起草催办、修改、预览发送

1. `Draft a chase-up for ORD-005.`
2. 如果追问联系人：`Address it to Maya.`
3. `Make it firmer but polite and ask for a reply by tomorrow noon.`
4. `Send it.`

**看什么：** 草稿可修改；第 4 步应展示最终发送预览，尚未送出。只有读完预览后的明确确认才会进入发送流程。

分两种展示方式：

- **未配置网关：** 可以在确认这是未配置环境后输入 `Send now.`，预期结果为未发送／连接器未配置，不能展示成发送成功。
- **已配置测试网关：** 先确认 Maya 已映射到专用测试收件人，再输入 `Send now.`；检查实际回执。不要对真实业务联系人做现场测试。

本项目的既往前端联调只验证过预览，没有验证真实外部送达。不要将本地 Confirm simulated send 的回执当成真实发送证明。

### 3.2 保存内部备注

1. `Open order ORD-005.`
2. `Add an internal note: Demo only - manager will verify the recovery plan.`
3. 如果追问目标：`Yes, ORD-005.`
4. 阅读预览，再输入 `Save it.`。

**看什么：** 确认订单目标不等于授权保存；应有最终预览和保存确认。结果明确为内部备注，不发送给客户或工厂。

这是演示写入，不要将第 4 步用于正式业务备注。后续恢复 MySQL 不会删除该条 SQLite 备注。

### 3.3 创建、修改条件提醒

1. `Remind me about ORD-005 tomorrow if there is no new activity.`
2. 如果追问具体时间：`Tomorrow at noon.`
3. 阅读预览后输入 `Confirm.`。
4. `Change that reminder to tomorrow at 2 p.m.`
5. 阅读新预览后再次输入 `Confirm.`。

**看什么：** 系统追问精确时间；保存 no_activity 条件；同会话、同订单、同条件的提醒原位修改，不重复建相同提醒。

#### 现场展示提醒触发（可选，放到所有日期相关测试之后）

固定时钟不会自动从 4 月 1 日走到 4 月 2 日。要观察到期：

1. 保留创建提醒的浏览器标签页，不点 New conversation。
2. 确保 ORD-005 的 last_activity_date 没有变成 4 月 1 日或更晚；数据更新测试后先恢复。
3. 在后端窗口按 `Ctrl+C`，执行：

```powershell
cd D:\GitProjects\DSS5105\threadpilot
$env:BUSINESS_NOW = '2026-04-02T14:01:00+08:00'
./backend/start.ps1
```

4. 刷新原浏览器标签页，保持页面在前台，等待约 30–60 秒，观察通知。
5. 通知一闪而过时，可在浏览器开发者工具 Network 中查看 `notifications/…` 请求；会话 ID 不要对外分享。
6. 结束后把业务时间改回 `2026-04-01T09:00:00+08:00` 并重启。

需要演示“条件满足不通知”时，用新的演示会话创建另一条提醒，截止前在 DataGrip 更新订单活动日期为演示当天并提交，再推进时钟。no_activity 只有日期精度，不能证明同一天的小时级活动。

`no_reply` 是另一种支持的条件，但它依赖已认证的回复事件接口；聊天里说“收到回复了”不能伪造回复记录。无上游接入时，无法证明现实中没有回复。

## 6. DataGrip 数据更新测试

### 6.1 先备份，再改数据

只修改演示库中的指定记录，不改表结构、主键或业务订单号。直接 SQL 会绕过 API 校验，所以示例同时维护 `version` 和 UTC `updated_at`。

在 **同一个 DataGrip Query Console、同一个连接会话** 中执行以下准备 SQL。临时表断开连接就会消失，因此同时把三条原记录导出为 CSV 或保存截图。不要整段执行后面的“修改”和“恢复”，现场一次选中一个步骤运行。

```sql
SELECT DATABASE(); -- 核对与后端 DATABASE_URL 的库名一致

CREATE TEMPORARY TABLE demo_order_backup AS
SELECT * FROM orders WHERE order_id = 'ORD-005';

CREATE TEMPORARY TABLE demo_production_backup AS
SELECT * FROM production_log
WHERE date = '2026-03-31' AND stage = 'ASSEMBLY';

CREATE TEMPORARY TABLE demo_workshop_backup AS
SELECT * FROM workshops WHERE workshop_id = 'W6';

SELECT * FROM demo_order_backup;
SELECT * FROM demo_production_backup;
SELECT * FROM demo_workshop_backup;
```

每张备份应只有 1 行，否则先停止检查。重复演示请先完成恢复，再换新控制台创建备份，避免覆盖原值。保持启动时 `SYNC_ENABLED=false`，不要同时导入表格或让其他人修改这些记录。

### 6.2 修改订单：证明多轮对话读取新数据

先新建对话：

```text
Open order ORD-005. Show its quantity, stage and last activity date.
```

然后在 DataGrip 执行：

```sql
START TRANSACTION;
UPDATE orders o
JOIN demo_order_backup b ON o.id = b.id
SET o.pieces = b.pieces + 7,
    o.current_stage = 'ASSEMBLY',
    o.last_activity_date = '2026-04-01',
    o.version = o.version + 1,
    o.updated_at = UTC_TIMESTAMP()
WHERE o.version = b.version AND o.status = 'IN_PROGRESS';
SELECT ROW_COUNT() AS changed_rows; -- 应为 1
```

确认影响 1 行后，单独执行 `COMMIT;`。如果不是 1 行，执行 `ROLLBACK;` 并检查当前数据，不要继续。

保留原聊天上下文，不刷新页面，输入：

```text
Refresh it now. Show its quantity, current stage and last activity date.
```

**通过标准：** 数量增加 7（种子为 500→507），工序变为 ASSEMBLY，日期变为 2026-04-01。右侧最新证据链接显示相同值和增加后的版本。

再打开 Orders 或 Dashboard，说明旧页面可能仍保留快照；刷新浏览器后检查新数据。聊天旁边的订单摘要卡也可能来自页面快照，核对实时值应以本轮回答和数据库证据为准。

### 6.3 修改产量：证明分析结果重新计算

```sql
START TRANSACTION;
UPDATE production_log p
JOIN demo_production_backup b ON p.id = b.id
SET p.pieces_completed = 600,
    p.version = p.version + 1,
    p.updated_at = UTC_TIMESTAMP()
WHERE p.version = b.version;
SELECT ROW_COUNT() AS changed_rows; -- 应为 1
```

影响 1 行后执行 `COMMIT;`，否则 `ROLLBACK;`。

新建对话并输入：

```text
Check assembly output on March 31, 2026 against the previous eight same weekdays.
```

**通过标准：** 当日产量变为 600，而不是旧值 455；历史基线不包含目标日，因此不应因为只修改目标日就变化。刷新 Dashboard，切到 ASSEMBLY 后，最新产量也应为 600。

### 6.4 修改外协厂：证明资格约束读取新数据

先在 Feasibility 中选择 TOPS、800 件、2026-04-25，勾选外协比较，运行 Compare scenarios，查看 W6 / Nimble Needle。

```sql
START TRANSACTION;
UPDATE workshops w
JOIN demo_workshop_backup b ON w.id = b.id
SET w.status = 'SUSPENDED',
    w.version = w.version + 1,
    w.updated_at = UTC_TIMESTAMP()
WHERE w.version = b.version AND w.status = 'ACTIVE';
SELECT ROW_COUNT() AS changed_rows; -- 应为 1
```

影响 1 行后执行 `COMMIT;`，否则 `ROLLBACK;`。刷新页面，重新进行相同外协比较。

**通过标准：** W6 显示 Suspended，不进入可用候选。这个测试改变资格，不保证最终推荐一定变化，因为原本最优候选可能就是另一家。

当前前端 Feasibility 使用固定 2026-04-02 起算的演示模型，只用于上述固定日期演示；实时承诺分析应使用聊天工作流。页面部分数据包说明和下载入口保留原型内容，不能用它们证明实时数据库连接。

### 6.5 恢复本次修改

在原 DataGrip 控制台中，**每段分别执行**。恢复也增加版本号，不把版本倒退。WHERE 条件避免覆盖已被其他流程再次更新的记录。

```sql
START TRANSACTION;
UPDATE orders o
JOIN demo_order_backup b ON o.id = b.id
SET o.pieces = b.pieces,
    o.current_stage = b.current_stage,
    o.last_activity_date = b.last_activity_date,
    o.version = o.version + 1,
    o.updated_at = UTC_TIMESTAMP()
WHERE o.version = b.version + 1
  AND o.pieces = b.pieces + 7
  AND o.current_stage = 'ASSEMBLY'
  AND o.last_activity_date = '2026-04-01';
SELECT ROW_COUNT() AS restored_rows;
```

影响 1 行后执行 `COMMIT;`；否则 `ROLLBACK;`，对比备份人工检查，不强行覆盖。

```sql
START TRANSACTION;
UPDATE production_log p
JOIN demo_production_backup b ON p.id = b.id
SET p.pieces_completed = b.pieces_completed,
    p.version = p.version + 1,
    p.updated_at = UTC_TIMESTAMP()
WHERE p.version = b.version + 1 AND p.pieces_completed = 600;
SELECT ROW_COUNT() AS restored_rows;
```

影响 1 行后执行 `COMMIT;`；否则 `ROLLBACK;` 并检查。

```sql
START TRANSACTION;
UPDATE workshops w
JOIN demo_workshop_backup b ON w.id = b.id
SET w.status = b.status,
    w.version = w.version + 1,
    w.updated_at = UTC_TIMESTAMP()
WHERE w.version = b.version + 1 AND w.status = 'SUSPENDED';
SELECT ROW_COUNT() AS restored_rows;
```

影响 1 行后执行 `COMMIT;`；否则 `ROLLBACK;` 并检查。只恢复实际执行过的测试；未修改的表不需要执行恢复。

最后查询三条记录、重新问 AI、刷新页面，确认业务字段恢复。版本号和更新时间变化是正常的。不要修改 imported_hash 来“消除差异”；后续导入冲突应按数据同步流程处理。

## 7. 其余功能点展示清单

### 7.1 页面内功能

| 功能 | 操作 | 判断是否通过 |
|---|---|---|
| 全局搜索 | 顶部搜索 ORD-005 或客户名 | 跳转 Orders 并筛选 |
| 订单筛选与分页 | Orders 切换客户、状态、交期、闲置条件；清除筛选 | 列表和结果数量随条件变化 |
| 订单详情与证据 | 打开订单、View evidence、导出订单 | 明细可查看，证据能核对；本地导出可能是页面快照 |
| Exceptions | 切换异常类别和等级 | 列表切换，能查看关联记录 |
| Risk orders | 选择不同订单 | 风险因素和关联订单可查看 |
| Feasibility | 修改数量、开关外协、比较情景、Save scenario | 展示假设、外协约束，保存到 Saved assessments |
| 本地备注 | 订单详情 Add note，输入“演示本地备注”并确认 | 页面备注和 Activity Log 出现记录 |
| 本地 Watch | Create watch，确认；Watches & receipts 中 Check now、Pause／Resume | 手动检查与启停正常；不等同于服务端定时提醒 |
| 模拟催办 | Draft chase-up，编辑、重新生成／复制、预览并 Confirm simulated send | Demo receipts 和本地日志出现记录；不会真的发送 |
| Activity Log | 从侧边栏进入，过滤类型、展开详情、Export audit JSON | 查看并导出本地记录；不是所有服务端操作 |
| Settings | 修改时间或阈值，Review changes，确认 | 刷新后本地偏好仍在；不启动定时日报 |
| 语音按钮 | 点击音符，编辑示例文字、Use transcript | 文字进入聊天；目前是真人编辑的转录演示，不是真实语音识别 |
| 对话记录与证据 | 提问两轮，定位问题、展开不同轮证据、导出 | 能查看当前会话及来源 |
| 停止／重试 | 发出问题后立即 Stop generating，再 Retry | 取消当前读取；重试重新发起请求，响应太快时可能来不及点停止 |
| 新会话／刷新 | 发起查询，刷新；再 New conversation | 刷新保留当前会话，新会话清空客户端上下文 |
| 手机布局 | 缩窄窗口或使用开发者工具手机模式 | 对话优先显示，菜单可展开，页面无横向溢出 |
| 本地重置 | 仅在所有演示结束后 Reset local actions & preferences | 清理浏览器本地记录，不删除 MySQL／服务端 SQLite |

停止读取不会撤销已经确认执行的操作，因此停止／重试演示使用只读问题。

### 7.2 API 补充功能（开发者演示）

这些能力不全有页面按钮，在 [Swagger](http://127.0.0.1:8000/docs) 中点击对应接口 → Try it out → 填写参数 → Execute。

| 能力 | 测试方法 | 观察点 |
|---|---|---|
| 只读 SQL Agent | `POST /api/ai/ask`，使用下面的 JSON | 返回答案和实际 SQL 查询结果；需要 AI_DATABASE_URL 的只读账号 |
