# Tool specification

One table for every tool the co-pilot can call. **B** = the backend (OpenAI model + MySQL): the model understands the question and
words the answer, and these tools do all the arithmetic and reading. **D** = the dashboard chat (built-in tools, no language model).
Every tool that reads data returns the source rows with its answer; every tool that acts waits for a confirmation and is logged.

## Definitions the tools share

* **Normal** (B7, B8, D7, the briefing, the Dashboard screen): the mean of the **previous 8 same weekdays** (Sundays excluded), with a band of
  **mean ± the larger of 1.5 standard deviations or 5% of the mean**. Fewer than 3 samples means "insufficient". The backend and the briefing are separate code;
  `backend/tests/test_one_definition_of_normal.py` holds them to identical numbers.
* **Risk** has one definition across both chats and the briefing: the **risk level** (B3, D11, the briefing and At risk card) is a day-by-day projection of
  the queue: overdue, high, medium or low (`docs/prediction_validation.md`). B3 computes it with the same engine as the briefing
  (`backend/app/discovery.py`), and `backend/tests/test_discovery.py` holds the two to the same level for every order on four mornings. B3 still reports
  **review triggers** (idle 7+ days, due within 7 days) as plain facts about what to look at, not as a second risk rule. The team's Dashboard screen keeps
  its own **priority score** and imported delay model for its task list; that is a separate screen and says so on it.
* **Feasibility** has two methods. B9 adds each stage's days in series on top of the whole backlog (very cautious). D10 returns a range from the queue and the
  recent arrival rate, and was checked against the simulator: on 180 test orders the range as first built held the real finish 69% of the time, so it is now widened by 3 working days at each end (94% on held-out futures; `docs/calibration.md`). Both state their assumptions; neither promises a date.
* **Capacity** in the briefing and D10 is usual output times a workshop factor estimated from completions, because the production log shows only about 59% of what
  ships (`docs/prediction_validation.md`, section 1). B9 uses the 20-day average output from the log, with no factor.

## How actions stay safe (B10 to B13, D15 to D17)

Preview first, with the action and its worst case. A confirmation key ties the preview to one order and one text; it expires after 15 minutes; the order record is
re-read before acting and the action is refused if it changed; confirming twice does nothing the second time; with no sender configured nothing is sent and the
answer says so. Every executed action is written to an audit log. The dashboard chat cannot send anything: it drafts, and logging happens after you confirm.
