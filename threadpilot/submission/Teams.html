3. How we worked together

Cadence. A weekly sync after the lecture, a mid-week check-in on the shared chat, and a sprint review before each deadline where every member ran the product themselves before anyone presented it. Decisions were written down in the repository (docs/SPRINT2_CHANGES.md, docs/SPRINT3_CHANGES.md) so a member who missed a meeting could read why something was done.

Ownership. Each feature had one owner and one reviewer. The owner wrote the regression tests for the feature; the reviewer wrote blind questions against it without seeing the implementation. The 26 Oct question sheet (59 questions written by all six, 24 wrong and 17 partial on the live build) is the clearest example: it was uncomfortable, it was reported as measured, and it produced seven fixes and 32 new evaluation scenarios.

Division between people and the model. Early on, members spent time hand-checking the model's arithmetic. The team moved to the principle "the model routes, code computes": humans write the tools and the tests, the model only reads questions and words answers. That changed what each member did day to day, from checking answers to designing checks.

Tools. GitHub with pull requests and CI on every push (tests plus the offline evaluation), a shared Claude project for notes and reviews, Tencent CloudBase for the shared deployment, and a shared question sheet for blind testing. Pair sessions were used for the hard pieces (the queue simulation, the Outlook OAuth flow, the live evaluation run).

What we would change. Start the evaluation set in week one rather than week six; it changed our design more than any other artefact. And deploy to the cloud earlier: several problems (CORS, the business clock, the MySQL ledger) only appeared once the system ran outside a laptop.
